# 📄 SyncNote: Архитектурная Выжимка (Контекст проекта)

## 1. Суть проекта
Приложение для синхронизации личных данных между **Windows (WPF/.NET 8)** и **Android (Kotlin/View)**.
*   **Цель:** Полноценная двусторонняя синхронизация заметок и файлов без облака (P2P по LAN/Wi-Fi Direct/BT).
*   **Статус:** Рабочий прототип. Синхронизация текстовых заметок работает end-to-end. Ведется разработка подсистемы «Отдельные файлы» (Backend F.1–F.5) и редизайн десктопа.

## 2. Технологический стек
| Платформа | Язык / Фреймворк | Ключевые библиотеки | Примечание |
| :--- | :--- | :--- | :--- |
| **Desktop** | C# .NET 8, WPF | `Microsoft.Data.Sqlite`, `QRCoder` | Логика вынесена в `SyncNote.Core`. GUI пока на системных стилях, планируется подключение темы (WPF-UI/ModernWpf). |
| **Mobile** | Kotlin, Android SDK 34 | Room-like manual SQLite, ML Kit Barcode | Нативный XML layout. SAF для выбора файлов. |
| **Database** | SQLite | Единая схема для обеих платформ | Таблицы: `notes`, `attachments`, `checklist_items`, `syncstate`, `seen_conflicts`. Новая: `files`, `file_syncstate`. |
| **Transport** | Raw TCP + JSON Frames | Big-endian length prefix + UTF-8 body | Шифрования нет (LAN trust model). Bluetooth RFCOMM и Wi-Fi Direct реализованы, но требуют hardware testing. |

## 3. Текущая архитектура синхронизации
*   **Модель данных:** Ревизионная (`rev`). Каждая запись имеет уникальный ID, номер ревизии и автора устройства.
*   **Алгоритм разрешения конфликтов:** Не Last-Write-Wins. При расхождении ревизий создается **копия конфликта** (новая запись с суффиксом `(копия конфликта)`), оригинал сохраняется. Идемпотентность обеспечивается таблицей `seen_conflicts`.
*   **Удаления:** Только Tombstone (`is_deleted=1`). Физическая очистка не производится автоматически (риск потери данных при асинхронном удалении).
*   **Транспорт:** Клиент отправляет `knowledge` (список известных ему ID+Rev), сервер отвечает дельтой изменений. Файлы передаются отдельными кадрами `file_begin/chunk/end` перед метаданными записи.

## 4. План разработки: Подсистема «Отдельные файлы» (Эпик F)
**Глобальная цель:** Позволить хранить файлы независимо от заметок, с дедупликацией по содержимому (SHA256) и полноценной синхронизацией.

### Ключевые архитектурные решения
1.  **Дедупликация:** Файл на диске хранится один раз под именем `{sha256hex}`. В БД могут быть несколько записей, указывающих на один хеш.
2.  **Новая таблица `files`:** Дублирует структуру `notes` (id, rev, updated_at, author_device, is_deleted), но вместо title/body имеет name, mime, size, sha256, stored_name.
3.  **Протокол расширения:**
    *   Новый кадр `file_register` (аналог `note_upsert` для файлов).
    *   Новый запрос `query_has_hash` → ответ `hash_response` (оптимизация трафика: если хеш есть у партнера, байты не шлем).
    *   Поле `file_knowledge` в сообщении `sync_begin`.
4.  **Исправление бага RAM:** Стриминг приема файлов на C# во временный файл (вместо буферизации всего тела в память, как было раньше).

### Этапы внедрения (Backend First)
*   **F.1 Миграция схемы:** Создание таблиц `files` и `file_syncstate` (v6→v7 Desktop, v7→v8 Mobile).
*   **F.2 Модуль FileIo:** Безопасное копирование с проверкой дедупа и стримингом хеширования.
*   **F.3 CRUD & DTO:** Реализация методов Add/Get/Delete/ApplyFile в Store и Repository. Логика конфликтов зеркалит заметки.
*   **F.4 Транспорт:** Интеграция новых кадров в StreamSession/SyncSession. Тесты Loopback.
*   **F.5 Purge Logic:** Очистка orphan-файлов после подтверждения доставки всем узлам.

> ⚠️ **Жесткое ограничение:** Не менять старые таблицы (`notes`, `attachments`). Весь новый код изолирован через Feature Flag `EnableSeparateFiles`. Обратная совместимость транспорта обязательна (старый клиент игнорирует неизвестные кадры).

## 5. Дизайн и UX (Решения приняты)
### Десктоп (WPF)
*   **Стиль:** Переход с «серого Tkinter-look» на современную тему (акцентный цвет индиго `#3F51B5`, паритет с мобильным брендом).
*   **Компоновка окна:**
    *   Шапка: Переключатель вкладок [Заметки | Файлы | Настройки] + Индикатор статуса синка.
    *   Список: Богатый ItemTemplate (превью тела, иконки вложений/чеклистов, бейджи статуса синка, локализованная дата).
    *   Детали: Редактор слева / Сводка справа (вместо пустого плейсхолдера).
*   **Настройки:** Карточный дизайн. QR-код генерируется автоматически при открытии вкладки сопряжения.

### Вкладка «Файлы» (UI Pattern)
*   **Список:** Слева, компактный, с иконками типов и бейджами статуса.
*   **Предпросмотр:** Справа, занимает основную область.
*   **Информация о файле (Спойлер):**
    *   Расположение: Наложение (Overlay) в нижней части блока предпросмотра.
    *   Поведение: Свернут в полоску «Информация о файле ▲». При клике/hover раскрывается вверх, показывая техническую инфу (SHA256, Rev, Author, Size) моноширинным мелким шрифтом.
    *   Принцип: Не мешает просмотру контента, доступно в один клик.

## 6. Известные проблемы и долги (Tech Debt)
1.  **Tombstone Growth:** Удаленные записи никогда не очищаются физически. Нужен механизм Waterfall Purge (этап F.5).
2.  **Conflict Fragility:** Поиск пар конфликтов сейчас идет по суффиксу заголовка (`title.endsWith("(копия конфликта)")`). Это хрупко. Для файлов сразу вводим явные связи или полагаемся на стабильный ID.
3.  **Hardware Verification:** Wi-Fi Direct и Bluetooth код написан, но не тестировался на реальном железе (пометки `NOT-VERIFIED`). Основной путь — TCP/LAN.
4.  **Docs Outdated:** README и спека протокола отстают от кода (упоминают несуществующие SSID, говорят про нереализованный BT). Требуют актуализации после завершения Epik F.
