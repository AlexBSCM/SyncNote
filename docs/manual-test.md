# Ручные тесты на двух устройствах (NOT-VERIFIED: needs hardware)

> F.7 (2026-09-29, железо 2511FPC34G): вкладка «Файлы» Android проверена
> на реальном телефоне — см. раздел «F.7 файлы на железе» внизу.
> Скриншоты-доказательства: `Screens/HW-*.png`.

Автоматизировано всё, что проверяется без железа (36 .NET-тестов, 4 JVM-теста,
loopback-сессии). Ниже — то, что требует физический ПК с Wi-Fi Direct
адаптером и физический телефон (эмулятор P2P не поддерживает).

## Подготовка

- ПК: `dotnet build SyncNote.sln`, запуск `SyncNote.Windows.exe`.
- Телефон: `gradlew assembleDebug`, установка `app-debug.apk`.
- Оба: включённый Wi-Fi (подключение к общей сети НЕ требуется и НЕ используется).

## T1. Сопряжение по QR

1. На ПК: строка состояния → «Сопряжение…» → «Принимать подключения».
   Ожидается: QR-код, «Код действует до …», адрес приёма.
2. На телефоне: «Синхронизация» → «QR» → навести на код.
   Ожидается: поля узел/порт/токен заполнились.
3. На телефоне: «Синхронизировать».
   Ожидается: «Готово: отправлено …, получено …», на ПК устройство
   появилось в «Доверенные устройства».
4. Повторная синхронизация с тем же токеном.
   Ожидается: отказ (токен одноразовый) — нужен новый код или пустой токен
   (доверенное устройство).

## T2. Передача заметки и вложения

1. На ПК создать заметку с текстом, чек-листом и вложением (любой файл).
2. Синхронизировать. Ожидается: на телефоне заметка, пункты, файл
   открывается побайтово идентичным (сверить размер/sha при необходимости).
3. Отредактировать на телефоне → синхронизировать.
   Ожидается: правка видна на ПК.

## T3. Обрыв посреди передачи

1. Начать синхронизацию большого вложения (десятки МБ), выключить Wi-Fi
   на телефоне посреди передачи.
   Ожидается: явная ошибка с обеих сторон, хранилища целы, повторная
   синхронизация завершается успешно, дублей нет.

## T4. Конфликт

1. Отключиться. Изменить одну заметку на ПК и на телефоне.
2. Синхронизировать. Ожидается: на обеих сторонах бейдж «Конфликты (1)»,
   в списке — копия «… (копия конфликта)», обе версии читаемы.
3. Разрешить тремя способами (текущая / копия / обе).
   Ожидается: выбор не приводит к скрытой потере версии.

## T5. Постороннее устройство

1. С телефона без сопряжения (чужой deviceId, без токена) попытаться
   подключиться. Ожидается: `hello_err`, доступа к данным нет.

## T6. Wi-Fi Direct вместо петли

1. На ПК создать автономную GO-группу (адаптер с поддержкой),
   в приложении вместо 127.0.0.1 указать адрес GO.
2. Пройти T1–T2 через P2P-адрес без общей Wi-Fi-сети.
   Ожидается: тот же результат, интернет не используется.

## T7. Bluetooth-резерв

## F.7 файлы на железе (VERIFIED 2026-09-29, adb + taps + screencap)

Стенд: USB, `adb reverse tcp:48211`, сервер ПК, токен через
`issuetoken.py`, синк через `SYNC_NOW`-intent. Доказательства —
`Screens/HW-*.png`, строки БД сверены прямым чтением `notes.db`
телефона (`run-as ... cat databases/notes.db`).

- Таб «Файлы» виден при флаге on; при `ENABLE_SEPARATE_FILES=false`
  таб отсутствует (в иерархии только tab_notes/tab_settings).
- Список: иконки/бейджи/мета/поиск/FAB/empty state — `HW-files-tab`,
  `HW-files-empty`.
- SAF-импорт реальных PNG через системный пикер — `HW-files-imported`
  (строка + жёлтый бейдж `● изменено`).
- Bottom sheet: шапка, пунктирное превью, спойлер с SHA256/ревизией —
  `HW-files-sheet`, `HW-files-info`; превью картинок рендерится
  (`HW-files-imgprev3`).
- Удаление: диалог → tombstone (`rev+1, is_deleted=1`, строка на месте,
  байты не удалены) → тост → список обновился — `HW-files-delete`,
  `HW-files-afterdel`.
- Синк ПК→телефон: `pushed=1 pulled=3 conflicts=0`, `hw-sync-test.txt`
  приехал с совпадающим sha256, бейджи зелёные — `HW-files-synced`.
- Синк телефон→ПК: tombstone `f4live.txt` и `pick2.png` доставлены
  (проверено таблицей `files` на ПК).
- Дедуп физический: каждый sha — один файл в `filesDir` (`ls`).
  UI-ветка «уже есть» — код-ревью (пикер системы не детерминирован
  для повторного выбора того же файла).
- Save As: файл создаётся; при `openOutputStream==null` теперь явная
  ошибка вместо молчания; `pendingSave` убран (состояние переживает
  смерть процесса через `entry` из arguments).

Найденные и исправленные баги (все покрыты железом):
1. Стартовый `sweepOrphanFiles` стирал байты `files` (учитывал только
   `attachments`); плюс тихий catch превращал занятость БД в удаление
   живых файлов, плюс нет защиты от гонки с параллельной записью.
   Исправлено: `files.stored_name` в known-множестве, отказ от чистки
   при любой ошибке чтения, пропуск файлов младше 60 с.
2. Кнопки шита капсом — добавлен `textAllCaps=false`.
3. `pendingSave` нигде не присваивался — Save As молча ничего не писал
   (0-байтные файлы). Заменён на `entry` из arguments + явная ошибка
   при `openOutputStream==null` + логи.

Известное ограничение (F-трек, обе платформы, НЕ чинить в F.7):
push tombstone без байтов роняет сессию (`sendFileDto` требует
`query_has_hash`→байты даже для `IsDeleted`). В реальных потоках байты
всегда есть (addFile атомарен, purge — только после сессий); поздний
 peer без байтов упрётся в это ограничение — нужен пересмотр протокола.
