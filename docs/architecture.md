Дата: 2026-09-26. Окружение проверено фактически, а не по памяти.

## 2. Решение по стеку

**Отдельные нативные клиенты + общий протокол синхронизации (JSON):**

- `windows/` — WPF (`net8.0-windows`), C#. Главное хранилище (источник истины):
  SQLite через `Microsoft.Data.Sqlite`, файлы вложений — в каталоге данных
  приложения, в БД только метаданные (имя, тип, размер, sha256).
- `android/` — нативный Kotlin, `targetSdk 34`, сборка Gradle Wrapper + AGP.
  Локальная копия: Room/SQLite + файлы вложений в app-specific storage.
- `protocol/` — описание формата сообщений и QR-пары (Markdown + JSON Schema,
  без кода, чтобы не дублировать реализацию на двух языках).

Причины против общего UI (.NET MAUI / Flutter): для Windows-цели MAUI нужен
Windows SDK и workload, которых нет; Flutter-плагинов Wi-Fi Direct под Windows
с паритетом нативных API нет. Нативные API P2P доступны только из нативного
кода, общий UI всё равно потребовал бы нативных модулей с обеих сторон.

## 3. Wi-Fi Direct: кто что делает (без магии QR)

Ограничение платформы, зафиксированное честно: QR-код сам по себе ничего
не подключает. Фактический сценарий:

1. **Windows** создаёт автономную группу (Autonomous Group Owner) через
   `Windows.Devices.WiFiDirect` (`WiFiDirectAdvertisementPublisher`,
   автономный GO) либо принимает входящее P2P-подключение с согласованием GO.
   Известный риск: не все WLAN-адаптеры/драйверы держат автономный GO;
   проверяется только на физическом ПК (`netsh wlan show drivers`:
   признаки размещённой сети / Wi-Fi Direct).
2. **QR-сопряжение** (доверенное, а не транспортное): Windows показывает QR
   с `{ groupSsid?, goAddress?, pairingToken(nonce 128 бит), expiresAt }`
   — токен краткоживущий (5 минут), заметок и постоянных секретов в QR нет.
   Android сканирует (CameraX + ML Kit Barcode), затем:
   `WifiP2pManager.discoverPeers` → находит устройство ПК (сверка имени/адреса
   из QR) → `connect()` (WPS PBC / ввод PIN отображается явно, не путать
   с запрещённым «отдельным PIN» — это системный WPS) → получает
   `groupOwnerAddress` (обычно 192.168.49.1).
3. **Защищённый сеанс**: TCP-сокет к GO + проверка `pairingToken` первым
   сообщением. Сервер сверяет nonce и срок, сохраняет **доверенный
   `deviceId`** (случайный GUID телефона, не MAC) в своём хранилище.
   Последующие сессии — по `deviceId` + новому nonce (re-pair без QR,
   отзыв — удалением доверенного устройства на Windows).
4. **Android 10+**: для P2P-discovery нужны разрешение
   `NEARBY_WIFI_DEVICES` (33+) и включённая геолокация; эмулятор Wi-Fi P2P
   **не поддерживает** — проверка только на физическом телефоне.

## 4. Bluetooth-резерв

Только после рабочего основного пути. Техника: RFCOMM SPP
(Windows: `Windows.Devices.Bluetooth.Rfcomm.RfcommServiceProvider`,
Android: `BluetoothSocket` по фиксированному UUID приложения).
Запуск — явной кнопкой «Подключиться по Bluetooth» на экране соединения,
с тем же токеном сопряжения. Ограничения: скорость, ручное сопряжение в
настройках ОС, MTU — документировать в README при реализации.

## 5. Модель данных и синхронизация (кратко, детали — этап 2)

- Заметка: `id` (GUID, стабилен), `rev` (монотонный счётчик на устройстве-владельце
  правки), `updatedAt` (UTC), `deviceId` автора правки, текст/форматирование
  (упрощённая разметка), чек-лист (позиции с флагами), вложения (мета + sha256).
- Передача — операциями (upsert/delete) с идемпотентным применением:
  повторная доставка той же `(id, rev)` не дублирует данные; вложения —
  чанками с sha256-контролем, прерванная передача не портит хранилище
  (сначала временный файл, затем атомарное перемещение).
- Конфликт: `(id)` изменён на обоих устройствах после общей базы —
  обе редакции сохраняются, запись помечается `conflict`, UI предлагает:
  «оставить версию ПК / телефона / сохранить обе». До выбора конфликт видим.
- Состояния соединения в UI: «не подключено», «ищем устройство»,
  «ожидаем подтверждение», «синхронизируется», «готово», ошибки + отмена
  длительных операций. Незавершённые функции помечаются, кнопки-пустышки
  запрещены.

## 6. Что можно проверить в этом окружении, а что — нет

- Можно: сборка WPF и unit-тесты ядра (SQLite, поиск, сериализация,
  идемпотентность, конфликты) через `dotnet build/test`; сборка
  debug-APK (`gradlew assembleDebug`, без подписи релиза); протокол —
  тестами поверх loopback-TCP (эмулирует сокет GO, но НЕ является Wi-Fi Direct).
- Нельзя без физических устройств: реальное P2P-обнаружение/соединение
  Windows↔Android, автономный GO на конкретном адаптере, WPS, Bluetooth-пары.
  Эти места помечаются `NOT-VERIFIED: needs hardware` и покрываются ручными
  тест-сценариями (`docs/manual-test.md`, этап 4+).
- Статус «подключено/синхронизировано» показывается только при фактически
  состоявшейся передаче; loopback-тесты так и называются.
