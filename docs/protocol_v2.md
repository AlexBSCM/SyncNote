# SyncNote v2 Sync Protocol

Транспорт: Raw TCP. Кадр: `[длина int32 BE][UTF-8 JSON]`.
Протокол симметричный: после обмена hello обе стороны шлют `sync_begin`,
затем каждая — свои дельты (вторая ждёт конца первой), затем `sync_end`.
Неизвестные типы кадров молча игнорируются (совместимость вперёд).

Отличия от черновика ТЗ (осознанно, по опыту v1):
- Нет `DELTA_PUSH`-конверта: каждая запись идёт отдельным кадром
  с квитанцией `applied` — идемпотентность видна сразу, а не в конце.
- Нет streaming-канала отдельно: чанки — те же JSON-кадры с base64
  (получатель пишет их в temp-файл, в RAM целиком файл не грузится).
- `FileDto` НЕ содержит `stored_name` (локальный путь не утекает;
  получатель выводит имя из `sha256`).
- Tombstone НЕ требует байтов ни на одной стороне (закрывает дыру v1,
  где push удалённой записи без тела ронял сессию).

## 1. Рукопожатие

`hello`: `{ "t": "hello", "deviceId": "...", "schemaVersion": 1,
"caps": ["files-v1"], "token?": "..." }`
`hello_ok`: `{ "t": "hello_ok", "deviceId": "...", "schemaVersion": 1,
"caps": [...] }`
`hello_error`: `{ "t": "hello_error", "reason": "bad token" | "version mismatch" }`

- Инициатор шлёт `hello` первым; респондер отвечает `hello_ok`.
- `schemaVersion` обязан совпасть, иначе `hello_error` + разрыв.
- **Одноразовый токен сопряжения (pairing):**
  - Респондер (принимающая сторона, обычно ПК) при старте pairing
    генерирует криптостойкий токен и показывает его в QR
    (`{"ip","port","token"}`). Токен сгорает при первом предъявлении
    (успех или отказ), повторный показ требует нового QR.
  - Если респондер ждёт токен (`expectedToken != null`), а в `hello`
    токена нет или он чужой → `hello_error` + разрыв, сессия не стартует.
  - Без токена с обеих сторон — обычная сессия (совместимость тестов).
  - Токен НИКОГДА не пишется в логи — только факт успеха/отказа.
  - Доверенных устройств (пропуск токена) в v2 MVP нет: каждая сессия
    требует свежего QR. Таблица `trusted_devices` — следующий этап.

## 2. Обмен знаниями

`sync_begin`: `{ "t": "sync_begin",
"knowledge": [{ "id": "...", "rev": 1 }],
"fileKnowledge": [{ "id": "...", "rev": 1 }],
"caps": ["files-v1"] }`

Обе стороны шлют `sync_begin` (инициатор первым). `knowledge` строится
по живым И удалённым строкам (tombstone тоже едут).

## 3. Дельты заметок

`note_upsert`: `{ "t": "note_upsert", "note": {
"id", "title", "body", "rev", "updatedAt", "author", "isDeleted", "baseRev" } }`

`baseRev` — `sync_state` отправителя на момент отправки.
Получатель применяет (см. §5) и отвечает на КАЖДУЮ запись:

`applied`: `{ "t": "applied", "id": "...",
"result": "Inserted|FastForwarded|NoOp|Conflict", "copyId?": "..." }`

## 4. Дельты файлов

Дедуп байтов через запрос (байты шлются только если их нет у пира):

`query_has_hash`: `{ "t": "query_has_hash", "sha256": "..." }`
`hash_response`: `{ "t": "hash_response", "sha256": "...", "has": true }`
`has` = есть живая строка с таким sha ИЛИ файл есть на диске.

Если `has == false` (и запись НЕ tombstone — см. ниже), отправитель шлёт:

`file_begin`: `{ "t": "file_begin", "sha": "...", "name": "...",
"mime": "...", "size": 123 }` (`size` ≤ 100 МБ, иначе разрыв сессии)
`file_chunk`: `{ "t": "file_chunk", "sha": "...", "data_b64": "..." }`
(чанки ≤ 64 КБ исходных байтов; получатель дописывает в temp-файл)
`file_end`: `{ "t": "file_end", "sha": "..." }`
(получатель сверяет sha256 temp-файла; несовпадение/размер — разрыв)

Затем всегда: `file_register`: `{ "t": "file_register", "file": {
"id", "name", "mime", "size", "sha256", "rev",
"updatedAt", "author", "isDeleted", "baseRev" } }`
и квитанция `applied` (та же форма, что у заметок).

**Правило tombstone:** `file_register` с `isDeleted=true` байтов НЕ требует
и НЕ запрашивает: получатель применяет только метаданные (вставка
tombstone / fast-forward в удаление / копия при расхождении).
Отправитель tombstone пропускает фазы `query_has_hash`/`file_begin`.

Получатель сверяет sha импортированного temp-файла с заявленным;
расхождение — разрыв сессии (fail-fast, ретрай позже).

## 5. Применение входящих (обе сущности одинаково)

Пусть `L` — локальная строка (нет = null), `D` — входящий DTO,
`S` — `sync_state` локально для этого id (0 если нет).

- `L == null` → вставить как есть (файл: материализовать байты, кроме
  tombstone — §4). `sync_state = D.rev`. Результат `Inserted`.
  Исключение: входящий tombstone неизвестного id — вставить tombstone
  БЕЗ байтов, `sync_state = D.rev`, `Inserted`.
- `D.rev > L.rev`:
  - `L.rev == S` (локально чисто, несент правок нет) → fast-forward
    (перезаписать поля, `sync_state = D.rev`). Результат `FastForwarded`.
  - иначе (локальная копия грязная: `L.rev > S`) → конфликт (§6).
    NB: условие сознательно строже v1 (`L.rev == S || D.baseRev >= S`
    тихо затирало локальные правки, когда стороны правили по 2+ раз.
    В парном обмене любое двустороннее расхождение — конфликт.
    `baseRev` остаётся в кадре для будущего multi-peer.
- `D.rev == L.rev`:
  - контент совпадает → `sync_state = max(S, D.rev)`. `NoOp`.
  - контент различается → конфликт (§6).
- `D.rev < L.rev` → `NoOp` (мы впереди; пир догонит в свою фазу).

Канонический хеш контента:
- заметка: `title + '\0' + body + '\0' + isDeleted` → SHA256 hex;
- файл: `name + '\0' + mime + '\0' + size + '\0' + sha256 + '\0' + isDeleted`.

## 6. Конфликты

Условие выше (§5, ветка «конфликт»): создаётся копия ОДИН раз на хеш
входящей версии (`seen_conflicts`: `NoteSeenConflict(id, rev, hash)` —
уже видели → `NoOp` без новой копии).

Копия: новый id, `rev = 1`, имя/заголовок + `" (конфликт)"`,
`isDeleted = false`, автор — текущее устройство, `sync_state = 1`.
Оригинал не трогается. Результат `Conflict` + `copyId`.

## 7. Обновление sync_state отправителем

По квитанции `applied` с результатом `Inserted`/`FastForwarded`/`NoOp`
отправитель ставит `sync_state = rev` отправленной записи.
При `Conflict` — не ставит (расхождение сохраняется до разрешения).

## 8. Завершение и ошибки

Каждая сторона после своих дельт шлёт `sync_end`: `{ "t": "sync_end" }`.
Сессия считается успешной, когда обе стороны отправили и получили всё
без исключений. Любая ошибка (сеть, sha, лимит, версия схемы) рвёт
сессию исключением; получатель уже применённых записей НЕ откатывает
(применение построчно идемпотентно — повторная сессия безопасна),
неотправленное уйдёт следующей сессией. «Полу-синхронизированных»
состояний нет именно благодаря идемпотентности, а не распределённым
транзакциям (их нет по дизайну).

## 9. Правило отправки (push trigger)

Пропуск записи — только если `rev <= собственный sync_state`
И (`rev <= knowledge пира` ИЛИ `запись — копия конфликта`).
Иными словами, шлём при неотправленной работе, при отставании пира,
но копии конфликтов обратно не катаем: они по построению синканы
(`rev == syncRev`) и нового для пира не несут (у пира либо оригинал,
либо своя копия того же содержимого). Маркер копии — суффикс
`" (конфликт)" в имени/заголовке. Поздний пир получает всё старое,
равные ревизии с расхождением шлют обе стороны.
